# Contributing Guide

This document summarizes the repository structure, build, tests, and code conventions for developers.
For library usage, see [README.md](README.md).

---

## Repository Structure

This is a Maven multi-module project.

| Module | Target | Spring | Compile |
|---|---|---|---|
| `pxl-spring-javax` | Java 8+, `javax.*` | Spring 5.3 / Boot 2.7 | source/target 8 |
| `pxl-spring-jakarta` | Java 17+, `jakarta.*` | Spring 6.2 / Boot 3.5 | source/target 17 |

> ⚠️ The source lives only in `pxl-spring-javax`. Do not edit `pxl-spring-jakarta` directly.

`pxl-spring-jakarta` contains no hand-written source.
At build time it is generated by file-system-copying the source tree of the sibling module `pxl-spring-javax` (`src/main/java`, and `src/test` for tests), applying the string substitutions below, and then compiling (via the `maven-antrun-plugin` in `pxl-spring-jakarta/pom.xml`).

```
import javax.annotation.   →   import jakarta.annotation.
import javax.validation.   →   import jakarta.validation.
import javax.servlet.      →   import jakarta.servlet.
```

Therefore:

- Always make code changes in `pxl-spring-javax`. To change `pxl-spring-jakarta` behavior, fix `pxl-spring-javax` and rebuild.
- Restrict `pxl-spring-javax`'s portable imports to exactly the three families above (`javax.annotation.*` / `javax.validation.*` / `javax.servlet.*`) — any other `javax.*` is not substituted and remains as-is in the jakarta variant.

The base package is `io.github.hclimkr.pxl.spring`. It holds only the `PxlSpring` facade and the `PxlSpringConstants` tuning constants; the five public `@Component @Validated` classes live in `component/`, and the boundary against the internal implementation (`internal/*`) is maintained by the `.internal.` naming convention (users do not reference `internal.*`).

## Development Environment

- JDK 17 must be on the PATH (`pxl-spring-javax` compiles to 8, but the build itself runs on JDK 17).
- Lombok is used throughout and is wired as an annotation processor in each module's `maven-compiler-plugin`. Enable the Lombok plugin in your IDE.

## Build & Test

`pxl-spring-jakarta` copies `pxl-spring-javax`'s source tree directly, so it does not depend on artifact install (the reactor order is preserved by the declaration order in the root `<modules>`),
but to build both modules at once it is recommended to run from the root.

```bash
mvn clean install                                        # Build both modules + tests
mvn -pl pxl-spring-javax clean install                   # javax module (source of truth)
mvn -pl pxl-spring-jakarta clean install                 # jakarta module (regenerates its sources)
mvn -pl pxl-spring-javax test -Dtest=PxlExcelExporterTests            # Single test class
mvn -pl pxl-spring-javax test -Dtest=PxlExcelImporterTests#someMethod # Single test method
mvn install -DskipTests                                  # Build without tests
```

- Tests are based on JUnit 5 (Jupiter) + AssertJ.
- Export result files are written to `pxl-spring-javax/target/test-outputs/` (`TestPaths.EXPORT_DIR`) as `*.xlsx` / `*.xls` / `*.zip`; since they are under `target/`, they are deleted by `mvn clean`.

## Test Writing Conventions

- Do not create new `*Tests.java`. The runnable classes mirror the main package layout: the five per-component classes (`PxlExcelImporterTests`, `PxlCsvImporterTests`, `PxlExcelExporterTests`, `PxlSampleExcelExporterTests`, `PxlExcelZipExporterTests`) under `io.github.hclimkr.pxl.spring.component`, plus `PxlSpringTests` (the facade), `PxlValidationTests` (`@Validated` argument checks) and `PxlRequiredHeaderStylerTests` (the javax/jakarta shadowing guard) in the root test package — so add methods to the relevant class. The non-component classes are covered by `internal/support/Pxl*SupportTests` and `logging/PxlPerformanceLoggingAspectTests`; only a genuinely new internal class earns a new test class of its own, next to those.
- Two of those reach into the `component` package from outside, and both do so to guard an invariant that has no observable behaviour of its own: `PxlCoreSupportTests` (every component takes its core from the shared holder) and `PxlPerformanceLoggingAspectTests` (the seventeen back-ends carry `@PxlPerformanceLogging` with their own class-name tag; the start methods and the facade do not). Keep the production dependency one-way — `component` → `internal.support` — regardless.
- Drive the behavioural tests through `PxlSpring` (`private final PxlSpring pxlSpring = new PxlSpring();`) rather than a component instance: that is the entry point the README documents, and the facade hands back the owning component’s own builder, so the coverage is identical. The exceptions are the two invariant tests above and `PxlValidationTests`, which contrasts a proxied component with the facade on purpose.
- Naming convention: class name = component, method name = `feature_situation_result` camelCase.
- Annotated DTO fixtures that are binding targets go under the `tcdata/` subpackage. Input data is mostly created directly in code within each test.
- Add regression/characterization tests together with any change that alters logic or performance.

## Code Conventions

- Write JavaDoc (`/** */`) and inline/block comments (`//`, `/* */`) in English.
- Validate required arguments of the public components with Bean Validation parameter annotations (`@NotNull` etc.) on `@Validated` classes — the `hibernate-validator` implementation performs the check at call time. Those annotations only fire when the call arrives through the Spring proxy, so a back-end that would otherwise dereference the argument must back them up with `PxlArgumentSupport.requireNonNull(...)` as its first statement. That keeps a plainly constructed component (`new PxlExcelExporter()`, which is also what `new PxlSpring()` does) inside the "every failure is a `PxlException`" contract instead of raising a raw `NullPointerException`.
- Every builder back-end method of the five components (the `...To*` / `...From*` methods — 17 in total) carries `@PxlPerformanceLogging(TAG)` (its own class-name tag). The AOP aspect is opt-in (`pxl.performance.logging.enabled=true`) and off by default.
- The working tree uses CRLF, but there is no `.gitattributes`; with `core.autocrlf=true` (this repo's setup) Git normalizes the committed blobs to LF. Take care not to mix EOLs after bulk substitutions.

## Pull Request

1. Branch off `main`.
2. Add/modify tests corresponding to the change.
3. Verify locally that `mvn clean install` passes.
4. Open the PR.

# PXL Spring 0.9.4

A maintenance release: the ZIP exporter reaches a file through a buffer, a file name the platform cannot read
as one stays inside the `PxlException` contract instead of escaping as an `IllegalArgumentException`, and the
new core underneath adds a per-thread language for diagnostic text. Built against
[PXL](https://github.com/hclimkr/pxl) 0.9.6, up from 0.9.5.

Pre-1.0 release with **no breaking changes**. One behavior change arrives with the new core: a `char`,
`Character` or `boolean`/`Boolean` column that sets `exportTrim` or `exportMasking` now writes different text,
because those two options had been doing nothing at all on exactly those three types. See the highlights below
and the [CHANGELOG](../../CHANGELOG.md).

## Highlights

  - **`exportZip().toFile(...)` is buffered.** A `ZipOutputStream` pushes its deflater output down in
    512-byte pieces, so writing straight onto a file meant a write call for every 512 bytes of the
    archive — around twenty thousand of them for a 10 MiB export. `.xlsx` members feel it most: they
    are already-deflated OOXML containers, stored at `NO_COMPRESSION` rather than compressed again,
    so they reach the file at full size. Every other destination here already had a buffer beneath it
    or needed none. Nothing to change at the call site, and nothing else about the destination moves —
    a failed export still leaves an unfinished archive on disk for the caller to deal with.
  - **A file name that cannot be read as one now leaves as a 415, not a 500.** commons-io refuses two kinds
    of name outright, with an unchecked `IllegalArgumentException` rather than an answer: one carrying a NUL
    character, on every platform, and on a Windows JVM one carrying a `:`, which it reads as an NTFS
    alternate-data-stream separator. Both used to escape this library as they were. An upload or resource
    named that way reached the controller as a 500, where this check's own answer is the 415 it already gives
    an unsupported extension; it is now refused with `HttpMediaTypeNotSupportedException` like any other name
    it cannot accept. Which names are refused is the platform's rule, not this library's, and is untouched —
    the full local path with its drive letter that some browsers upload is accepted as it always was.
  - **The same name in a ZIP entry is refused before anything is written.** There the raw exception came out
    of the per-entry deflate-level lookup, inside `writeEntries` — past the point of no return for the three
    destinations that write as they go: the caller's stream had taken bytes, the file destination had created
    its file, and `toResponseStreaming` had committed its download headers. The check now runs in
    `validateEntries()`, beside the path and duplicate checks that were moved there for the same reason, and
    answers `PxlArgumentException` while every destination is still untouched.
  - **What the new core brings with it.** [PXL 0.9.6](https://github.com/hclimkr/pxl/releases/tag/v0.9.6) is
    underneath, and four of its changes are visible through this library. Diagnostic text has a per-thread
    language now — `Pxl.setThreadMessageLocale(Locale)`, cleared with `Pxl.resetThreadMessageLocale()` —
    which is the tier a web application was missing: the only call available before set the language for the
    whole process, so a request setting its own would have changed the messages of every other request in
    flight. Set it from `LocaleContextHolder.getLocale()` as a request begins and clear it in a `finally`,
    since the container hands that thread back to a pool; those two calls are the whole integration, and
    `Pxl.setMessageLocale(Locale)` still means exactly what it meant. A missing sheet is reported with the
    names the source does hold — the workbook's own on an Excel import, and on a CSV import the sheet names
    derived from the files or resources you handed over. `exportTrim` and `exportMasking` reach `char`,
    `Character` and `boolean`/`Boolean` columns, which had been ignoring both *(behavior change)*. And a
    `char` column you never filled in exports as its `exportNullString` rather than the `?` the XLSX writers
    were quietly substituting for its NUL.
